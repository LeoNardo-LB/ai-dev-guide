# 观测与取证（Evidence）

> 代码改动后通过一切可观测手段获取证据的操作手册：日志、数据直查、网络、UI dump、截图、证据链组织与并行委派。
> 本文回答「怎么拿证据」；「我算完成了吗」见 [verify.md](./verify.md)；「变更后重测什么」见 [regression.md](./regression.md)。

## Use when

- 调试、取证、验证运行时行为前
- 任何代码改动验证、声称完成前（与 verify.md 铁律配合）
- 需要组织证据链、或并行委派验证节点时

## 1. 可观测手段全景

| 手段 | 观测对象 | 何时用 | 要点 |
|------|----------|--------|------|
| 日志 | 应用运行日志（关键 tag） | 验证逻辑分支/状态流转/错误路径 | 按进程 + tag 过滤（§2） |
| 本地数据直查 | 数据库/本地存储 | 验证落盘、持久化、迁移 | 直查数据，不能只看 UI（§3） |
| 网络 | 客户端与服务器 HTTP/流式 | 端点行为、错误响应、事件流 | 先服务器直测再判归属（§4） |
| UI dump | 界面节点树（节点 + bounds） | 节点存在性/位置/滚动有效性 | bounds 对比，不做哈希（§5） |
| 截图 | 界面视觉状态 | 人工或视觉模型确认 | 静态快照，配合 UI dump（§5） |

平台具体命令（日志抓取/数据库直查/截图工具）属**栈事实**：按本项目栈填写在 [stack-profile.md](../stack/stack-profile.md)（命令符号定义处 §5）；[android-kotlin-example.md](../stack/android-kotlin-example.md) 是栈档案的填写范例（不含观测命令）。

### 1.1 单一通道不做最终判定

每种仪器都有已知盲区——任一单通道的「没看到」不构成「不存在」的证明；结论必须 ≥2 独立通道互证（[verify.md](./verify.md) §3）或以第二通道复核阴性结论。

| 仪器 | 已知盲区（示例，随项目沉淀） |
|------|------------------------------|
| UI 树 dump | 独立弹出窗口/自绘内容可能整块失明（失明 ≠ 不存在） |
| 视觉模型 | 小目标坐标幻觉率高——只用于描述与仲裁，禁让报坐标 |
| 截图哈希 | 状态栏/时间噪音导致假阳假阴（§5 已禁） |
| 一次性日志快照 | 缓冲轮转吃掉早期日志（§2 连续档） |

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 发现新盲区/仪器伪影（工具性假象）当场登记进本表，两源互证后沉淀为断言禁令 | 同一伪影反复误导定罪 |
| 2 | 仪器失明区改用第二通道取证（像素采样/日志/数据直查），不以单通道阴性下结论 | 「看不到」被当成「没有」 |

## 2. 日志观测

### 2.1 抓取规范

- 按进程 + tag 过滤抓取；裸抓取会被系统噪音淹没，采集结果不能作为证据
- 崩溃/ANR 从崩溃缓冲区单独抓取
- 长测试（>1 分钟）的断言基于**持续写入的日志文件**区段（记录起始行号再取区段），而非一次性快照——设备/服务缓冲会分钟级轮转，快照会吃掉早期证据
- 具体抓取命令以 [stack-profile.md](../stack/stack-profile.md) §5 命令符号区为真相源（按栈填写，不在此复制命令模板）

### 2.2 关键 tag 速查表（随代码演进维护）

| Tag | 观测内容 | 维护责任 |
|-----|----------|----------|
| 项目统一日志门面 | 应用内日志同源聚合（进诊断屏） | 新增关键逻辑时登记 |
| 模块 tag | 各模块关键行为与决策值 | 改动相关代码时同步增删 |

维护纪律：新增关键决策点后登记或更新本表，删除的 tag 同步移除。违反后果：速查表陈旧 → 验证时找不到正确 tag，抓不到有效证据。

### 2.3 埋点要求

| 要求 | 说明 | 违反后果 |
|------|------|----------|
| 关键逻辑必有可观测输出 | 新增关键决策点（判定/回退/防御命中）必须埋点，记录决策与关键值 | 逻辑不可证 |
| 日志可行动 | 含关键值（版本/状态/响应头/body 预览） | 仍需猜 |
| 频率分级 | 高频路径用 DEBUG 门控；用户可见错误记录堆栈 | 日志风暴淹没信号 |

## 3. 本地数据直查

- 验证「是否落盘/持久化/迁移生效」必须直查本地数据，UI 显示不能替代
- 违反后果：只看 UI → 缓存/落盘错误被误判为正确
- 对**运行中的有状态存储**（活库/活缓存）取证：先做一致性/完整性校验，结论以校验通过时的快照为准——运行中文件可能读到半写状态

## 4. 网络层观测

- **先服务器直测，再判归属**：客户端报错时先直连预试——服务器可达且响应正确 → 问题在客户端；反之在服务器
- 不确定端点/返回结构时先实测拿真实响应，禁止凭猜测假设 API 行为
- 违反后果：把服务器行为当客户端 bug 修，方向性返工
- **受端效果红线**：网关/服务器返回 ok ≠ 成功——成功必须有受端效果证据（执行了/恢复了/UI 状态变化了），发起端视角不构成证据（[acceptance.md](./acceptance.md) §3）

## 5. UI 观测

| 规则 | 说明 | 违反后果 |
|------|------|----------|
| 截图 + UI dump 结合 | 截图看视觉，dump 看节点与 bounds | 单看截图无法断言位置 |
| 动态断言用 bounds 对比 | 滚动类验证记录 2-3 个节点前后 bounds，双向各测一次 | 单向无法区分「失效」与「已到边界」 |
| 截图哈希不可靠 | 状态栏/时间噪音导致假阳假阴，不做哈希对比 | 误判 → 无效证据 |
| 关键点动态定位 | 键盘弹起/通知横幅会位移界面——固定坐标必错；点按前查 UI 树取实时坐标 | 点错目标，实验作废 |
| 观测输出须验证新鲜 | dump/截图前先删旧文件；文件时间戳对不上即弃用 | 陈旧文件被当成新证据 |

### 5.1 像素取证（色值/对齐/在场性）

- 断言「某区域是什么颜色/某元素在场」用像素采样：预先登记基准色锚点，采样对照，或做区域色彩统计。
- 暗色/亮色主题下禁止亮度启发式判断（感知亮度 ≠ 视觉呈现）——用锚点色值对照。

### 5.2 视觉模型使用纪律

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 视觉模型只做**描述性/仲裁性**提问（「图中是否有 X？两图何处不同？」） | 模型顺嘴编造 |
| 2 | 禁止让视觉模型报小目标坐标（幻觉率高）；坐标一律来自 UI 树/像素采样 | 点按/断言错位 |
| 3 | 禁止引导性提问（「这里是不是有 bug？」）；串行调用避免互相污染 | 结论被提问预设 |

### 5.3 帧级取证（时间性现象）

- 闪烁/跳动/过渡类现象：录屏 → 抽帧 → 逐帧对比（位移/内容变化出现在哪一帧）——帧序列是客观证据，可数帧定罪。
- 性能面：帧率/卡顿占比/耗时分位值按固定参数采集（同一场景同一参数，A/B 可比；基线纪律见 [regression.md](./regression.md) §3.1）。

## 6. 证据链四环

```
操作步骤（可复现） → 原始证据（文件/输出） → 断言（预期 vs 实际） → 结论
```

| 环 | 要求 |
|----|------|
| 操作步骤 | 记录环境（设备/版本/服务器）、前置条件、操作序列 |
| 原始证据 | 落盘到证据目录（截图/dump/log/DB 查询/测试报告/diff） |
| 断言 | 每个证据旁标注预期值并记录实际值 |
| 结论 | 断言全部满足且 ≥2 维度交叉（[verify.md](./verify.md) §3）才可下结论 |

归档规则：修复类证据随 commit；发版类归档到 release 目录；研究类入 docs/research/ 并在文档引用。多步验证用 [verification-node.md](../templates/verification-node.md) 模板组织。

## 7. 并行验证节点（subagent 委派）

### 7.1 适用场景（满足任一）

| # | 条件 |
|---|------|
| 1 | 至少 3 个互相独立的验证节点（不同能力域/服务器/UI 路径） |
| 2 | 单节点耗时超过 1 分钟（等待流式/网络/模拟器） |
| 3 | 主 agent 上下文预算有限 |

### 7.2 节点划分原则

| # | 原则 | 违反后果 |
|---|------|----------|
| 1 | 按能力域切分；节点间零共享可变状态 | 并行干扰，证据互相污染 |
| 2 | 每节点自带完整自包含 prompt（环境/步骤/断言/证据路径） | subagent 无法执行 |
| 3 | 证据落盘分离（证据目录/node-N/） | 写冲突、归属不明 |
| 4 | 独占资源（设备/共享环境/同一 checkout 的构建目录）同时只允许一个执行流操作（[acceptance.md](./acceptance.md) §4） | 并发操作践踏，证据污染 |

### 7.3 委派协议

```
主 agent：划分节点（每节点写清环境/步骤/断言/证据路径）→ 并行 launch →
          等待全部返回 → 汇总交叉矩阵 → 抽查复核至少 1 节点证据真实存在
subagent：按清单执行 → 采集原始证据落盘 → 返回结构化结果（通过/失败 +
          断言对照 + 证据文件列表）；禁止代替主 agent 下「完成」结论；
          执行期间禁止分析/归因/修复——只观测与记录；失败项继续后续独立项，
          依赖项标 BLOCKED-by-编号（分析归主 agent）
```

| # | 合并规则 | 违反后果 |
|---|----------|----------|
| 1 | 全部返回后构建交叉矩阵（节点 × 维度），每格标注证据文件 | 证据散落无法核对 |
| 2 | 任一同结论节点失败 → 整体结论失败，定位差异（环境/竞态/真 bug） | 部分成功掩盖整体失败 |

## 8. 代码改动标准观测流程

```
1. 改动前：确认可观测点（tag/表/端点）；缺失 → 先埋点再改逻辑
2. 改动后：构建通过 → 测试通过（含新增用例）
3. 运行：安装目标场景，跑目标路径
4. 采集：日志（进程过滤）/ 数据直查 / 截图 + dump
5. 对照断言：观测值等于预期值？至少 2 独立维度互证（verify.md §3）
6. 回归与完成声明：按 regression.md 执行；证据齐全才声称完成
```
