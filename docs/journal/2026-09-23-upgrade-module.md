# 2026-09-23 <批次：upgrade-module>

> 状态：已完结
> 来源：用户提案（「升级了本地内容，客户端如何升级？全量重新覆盖不太好——是否需要做一个升级模块？」）
> 关联：docs/journal/2026-09-23-script-audit-sandbox.md（同日脚本审计批次，upgrade.sh 四缺陷修复为其前置）

## 目标

把 upgrade.sh 从「只报告」升级为分级执行的升级模块：全量重覆盖永不发生，本地化修改零丢失，升级流程可闭环。

## 过程与证据

- 第 1 轮（设计）：用户痛点成立——现状 report-only，apply 动作全人工；且基线无部署档案，「上游新增 vs 当初裁剪」不可区分。定案三方分级模型：本地 vs 基线 vs 上游 → 可安全同步 / 双方修改 / 已合并保留 / 本地领先 / 上游新增 / 当初裁剪 / 上游已删除 / 本地新增，八级各配动作。
- 第 2 轮（实现）：upgrade.sh 重写为四子命令模块（report/apply/merge/baseline，默认 report 完全向后兼容）；init.sh 基线写 profile 档案头；merge 的 base 内容取上游 git tag v<部署版本>（哈希基线无内容，tag 是现成的版本化快照——发版 tag 纪律在此兑现价值）。
- 第 3 轮（E2E + R5 回归，三处设计缺陷被当场抓住）：
  - 缺陷 A（严重）：apply 曾用全量重写刷基线——会把本地化修改洗进基线（bug.md 从「双方修改」变「可安全同步」），下一次 apply 即覆盖本地内容。修复：apply 改增量刷新（只登记本次同步项），全量重写仅属显式 baseline 子命令。RED→GREEN（二次 apply 后本地行原样）
  - 缺陷 B（语义）：人工合并 + baseline 刷新后文件落在「基线==本地 且 ≠上游」→ 被归可安全同步，纯上游版会覆盖合并稿。修复：baseline 刷新时给与上游不一致的部署面文件打 #merged 保护标记，分类单列「已合并保留」桶，apply 永不覆盖。RED→GREEN（apply 三连击双侧内容完好）
  - 缺陷 C（R5 抓获，分类模型级）：部署是**带变换的复制**（scrub 清洗）——部署态≠源态是合法差异，但分类把它误判为「上游演进」（全新 --no-example 部署误报可安全同步 4）；且 apply 直接抄源文件会绕过清洗管线、重引入悬空链接。修复：基线记**双哈希**（部署态 + 源仓源态 #src=），分类区分「变换等价（归一致）」与「源态真演进」；apply 复制后重跑同一 scrub 管线再入册。RED→GREEN（R5 归零 + 裁剪模式 E2E 全绿含部署门禁通过）
- 第 6 轮（AGENTS 保护六场景核查，用户问「会不会破坏用户自己的 AGENTS.md」——实证抓三缺陷并修复）：重复 init 曾覆盖用户合并中的 .new 草稿（改为保留+警示跳过）；apply 入口重建被「无可同步项提前退出」短路（模板演进不生效——重构为始终检查）；合并稿+baseline 刷新后曾被判定「未动过」可被直生覆盖（基线给 AGENTS.md 打 #merged：内容≠模板重生成实例即含自定义，apply 永不直生；.new 草稿被用户编辑过则 apply 亦不覆盖）。终验 9/9 全绿 + R15f 断言固化。
- 第 5 轮（跨版本真实矩阵 + AGENTS 入口重建，四缺陷被当场抓住）：用户问「能确保可用吗」——补真实场景（git worktree 检出真 v2.6.2/v2.6.3 tag 部署 → 升级到本版），暴露并修复：
  - 缺陷 D（功能盲区）：运行时脚本（check/_gates/backlog/scan-secrets 等 8 件）不进 manifest 分类循环——跨版本升级后目标仍跑旧版脚本（正是历次修 bug 的对象）。修复：RUNTIME 清单纳入三方分类与 apply（与 init.sh 1b 复制清单同步）
  - 缺陷 E（事实洗白）：旧基线升级时档案被写成 no_ui=0（None or 0 手滑）——裁剪事实丢失，下一轮 apply 强补 ui 文档。修复：档案缺失时从部署现状推断并一次性归一
  - 缺陷 F（意图违背）：ui/stack-example 组文档缺席被误判「上游新增」强补进裁剪部署。修复：裁剪组缺席即「当初裁剪」（档案优先，旧基线按组推断）
  - 缺陷 G（闭环缺口）：AGENTS 根级实例一律丢人工合并 .new，未改过的项目升级后门禁仍红。修复：未被本地修改（当前==基线可证）→ 直接重生成生效；改过 → .new
  附带：apply 清洗扩为全系统目录幂等重洗（上游未变但部署形态带旧债的文件一并修复），哈希变化文件同步刷基线。
  终验矩阵 11/11 全绿：C 场景（v2.6.2 --no-ui --no-example → v2.7.0）裁剪不补/AGENTS 无残留引用/门禁通过/档案保留 no_ui=1/归类正确/二次幂等；A 场景脚本升级+门禁绿；B 场景 sysdir 本地化与改过的 AGENTS 均不被覆盖且 .new 就位。
- 第 4 轮（全场景复验，2026-09-23）：
  - 全链路：部署→report（可安全同步2/双方修改1）→apply（同步3项+门禁绿+双方修改保持1）→merge（.base/.yours/.theirs/.merged 四工件，base 来自 v2.6.3 tag，merged 自动合并干净含双侧）→写回→baseline→终态零待办 GREEN
  - 兼容：旧版基线（无档案头/无标记）退化正确；无子命令/带目录名无子命令两种调用形态等价
  - 防呆：未知子命令 exit 2；baseline 在门禁红（注入影子卡）时拒绝刷新 GREEN
  - 全仓：check.sh 十门禁通过；selftest R1-R15 全绿（R15a-e 五断言固化本模块）

## 完结迁移区

本批无卡片迁移（源仓无 backlog 账本）。

## 遗留

- merge 的 base 依赖上游 git tag v<部署版本> 存在：源仓未打 tag 的部署（或 tag 被删）退化为双方对照（无 .base/.merged）——发版 tag 纪律是前置承诺，已在 onboarding 第 4 节声明
- apply 不自动重实例化 AGENTS.md（模板派生物，含目录名/裁剪上下文）：需要时重跑 init.sh 生成 AGENTS.md.new 人工合并——机械派生与人工内容的边界，保持显式
- 上游已删除文件不提供自动清理（保留 + 归档建议）——删除属不可逆动作，留人工决策
